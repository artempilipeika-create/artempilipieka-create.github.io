## Backup and real restore

Use `backend.v2.backup.backup` with an unused private destination. It holds the exclusive backup advisory lock, runs native `pg_dump --format=custom`, copies registered bytes and verifies SHA/size. Passwords are passed in the subprocess environment, never command arguments or logs.

Restore only into a **new empty staging database** whose name contains `_restore`, and a **new empty private storage root**, using `backend.v2.backup.restore`. The target must carry the same staging namespace. Never restore over working staging. Native `pg_restore --single-transaction` is followed by private byte restoration and verification.

`backend.v2.stage05_operator.verify` checks all Stage 4 hashes plus exact PostgreSQL snapshots of documents/templates/history policy/users/sessions/roles/grants/assignments. Every PDF must match its calculation/order/revision and presentation hash, registered SHA and actual bytes.

`retire_restore(settings, synthetic_operator_email, checkpoint="stage05-template-v2")` retires the temporary operator and Stage 5 synthetic users, revokes sessions/grants, removes temporary admin role, performs backup, creates a unique restore database/root, restores and compares the full state. It writes `/mf-private/stage05-template-v2-restore-evidence.json`. This is a deliberate operator command, without an HTTP endpoint.

Run `verify_persistence(settings, checkpoint="stage05-template-v2")` in a fresh deployment. It compares current state with the successfully restored checkpoint, including authorization metadata and every PDF hash. Restore tests do not establish off-site backup retention or production recovery.

## Deployment safety

The Railway connector's `redeploy` can replay an old deployment snapshot. For changed maintenance commands, use `deployServiceTool` with the **explicit tested commit SHA** and current saved configuration. The explicit deployment commit does not persist `source.commitSha`: update that pin separately, inspect pending changes, commit only the scoped API service change and re-read configuration.

Finish with `python -m backend.v2.serve`, all probe/bootstrap modes off, temporary email/password variables empty, original mail seal key preserved, transport/dispatch disabled. Confirm actual deployment metadata and persisted source pin agree. Do not use branch HEAD implicitly.

## PDF versions and boundaries

Current server template `mf-preliminary-a4-v2` (v1 artifacts retained), ReportLab 4.4.9, repository-owned DejaVu Sans regular/bold with SHA checks and license. `asset_sha256` includes renderer/projection source and font checksums. Changing template implementation requires a new version; it cannot silently change already-bound artifacts. Generated byte metadata is deterministic and no network requests occur while rendering.

Only one immutable calculation supplies financial values. `document_projection.project` copies amounts, units and discounts without recalculation; the cabinet consumes the same projection. Presentation snapshot also freezes client/order display data and document date. Stored PDFs are not regenerated on download.

Generation serializes by calculation advisory lock. Repeats of the same calculation/template return the same file. Version/binding + audit + paused local outbox commit together. Private file manifest is durable before final binding: interruption can leave an unbound registered PDF for reconciliation, but all PDF gateways and client listings deny that file. There is no automatic orphan deletion.

Limits: 500 rows, 500 KB serialized presentation, 2,000 characters per field, 100 pages, subprocess 512 MiB / CPU 20 s / wall 30 s, output 10 MB. Text is escaped, unsupported glyphs fail explicitly, active content and external assets are not accepted. Renderer failure returns a bounded client error, not internal diagnostics.

## Authorization and visibility

`documents.generate` is explicit, scoped own for clients; managers/admins need separately granted permission. Downloads require `orders.read` + `files.preliminary_pdf.read`; managers must also be currently assigned; accounting additionally needs `orders.prices.read`. Viewer/admin require explicit scope/grants. Production and service_agent role ceilings deny preliminary PDF. Existing aliases delegate to this same gateway. OBLX/internal content is denied before document lookup and never enters account listings.

NC-08 stays open. `mf_history_policy.completed_visibility_days=NULL`, `direct_history_access=true` preserve history. A nullable `mf_orders.completed_at` can carry a future imported legacy completion date; Stage 5 does not set business completion. A configured day limit filters visibility only, never deletes rows or bytes. Direct access can be configured separately. Tests cover both modes.

## Rollback

1. Stop new staging writes; preserve a fresh Stage 5 backup first.
2. For an application-only rollback, deploy a known tested Stage 5 commit compatible with migration 0005 and the stored template version. Do not edit an applied SQL migration or mutate documents.
3. To return fully to Stage 4, create a new isolated staging rollback database/private root and restore the verified **pre-stage05** backup into it. Validate the Stage 4 revision/calculation/file state against `pre-stage05.json`.
4. Point only this staging API's `MF_DATABASE_URL`, host/name references and private root to that isolated restored target; deploy the Stage 4 runtime `af6e58466a880eff17ccb1feb7f02e7f8db548f9` and align its persisted source pin. Preserve the original Stage 5 DB/root for forward recovery. No in-place downgrade/drop and no production credential references.
5. Confirm exact 0001–0004 migration checksums, noindex/no-store, disabled Agent/dispatch and protected service deployments.

A Stage 4 binary intentionally fails readiness against a Stage 5 schema. Merely changing the Git SHA is not a complete schema rollback.
